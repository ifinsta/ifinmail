# Environment reference

Two layers. Do not mix them.

| Layer | File | Names | Example |
|---|---|---|---|
| Django runtime (local dev, CI, containers) | root `.env` (copy of `.env.example`) | `DJANGO_SECRET_KEY`, `DJANGO_ALLOWED_HOSTS`, `DB_*`, `REDIS_*`, `MAIL_*` | `DJANGO_SECRET_KEY=...` |
| Host provisioning | `provisioning/.env` (generated by `make provision DOMAIN=...`) | `SECRET_KEY`, `DJANGO_ALLOWED_HOSTS`, `APP_DB_PASSWORD`, `REDIS_PASSWORD`, `DOMAIN`, `MAIL_*` | `SECRET_KEY=...` |

`provisioning/docker/docker-compose.yml` maps provisioning → runtime:

| provisioning/.env | → runtime inside api/worker/beat |
|---|---|
| `SECRET_KEY` | `DJANGO_SECRET_KEY` |
| `DJANGO_ALLOWED_HOSTS` | `ALLOWED_HOSTS` |
| `APP_DB_PASSWORD` | `DB_PASSWORD` + `DATABASE_URL` |
| `REDIS_PASSWORD` | `REDIS_URL` + `CELERY_BROKER_URL` |
| `DOMAIN`, `MAIL_DOMAIN`, `MAIL_HOSTNAME`, `DKIM_SELECTOR` | same names |

Rules:

* Set hosts only via `DJANGO_ALLOWED_HOSTS` locally. In production compose
  injects `ALLOWED_HOSTS` from it. `production.py` accepts either, with
  `ALLOWED_HOSTS` taking precedence.
* Secret key: `base.py` accepts `DJANGO_SECRET_KEY` first, then `SECRET_KEY`
  fallback (provisioning name). Production fails fast with a clear message
  instead of a bare `KeyError`.
* `DJANGO_SETTINGS_MODULE`: `development` locally (`manage.py` default),
  `production` in containers, `testing` under pytest (`pyproject.toml`).
  `.env.example` ships `development` so `make check` never surprises with
  `check --deploy`.
* `USE_SQLITE=1` (or unset `DB_HOST`) uses `db.sqlite3` + `LocMemCache` for
  local dev with no Postgres/Redis. Unset it and set `DB_HOST`/`REDIS_URL` to
  test against real services.
* Never commit `.env` or `provisioning/.env`. Both are gitignored. Rotate any
  secret that touches the repo.
